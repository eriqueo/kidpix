# Ungroomed backlog (historical input)

Do not implement directly from this file. These ideas predate the active queue and have
been reconciled only enough to separate shipped behavior from the remaining need. Promote
a verified user journey into `current.txt` before implementation.

## Persist selected UI state across reloads

Remaining idea: restore the selected tool, each tool's selected subtools, current color,
and palette after a page reload. Tools do not currently remember their subtool choices even
while the app stays open: each tool click rebuilds the submenu and re-highlights fixed defaults
(`js/init/kiddopaint.js` init_tool_bar). The four persistence cases in
`tests/e2e/tool-switching.spec.ts` are skipped with that reason until this is promoted.

The old request also asked for undo/redo across reloads. That conflicts with the current
intentional performance boundary: undo/redo is bounded in-memory `ImageData`, while only the
current drawing is persisted. Reintroducing cross-reload history would require a new bounded,
asynchronous persistence design and iPad performance evidence; it is not a small localStorage
change.

## Add a user-facing settings and storage page

Remaining idea: give a grown-up one place to inspect and change user settings and to clear
app-owned persistent data. Candidate controls include keyboard shortcuts, Small Kids Mode,
the current drawing, saved ColorMe pages, SlideShow projects, custom sounds, stamp overrides,
and remembered selections if that feature is promoted.

Before promotion, inventory the actual storage owners and declare retention/cleanup behavior.
Do not implement a generic "show all localStorage" surface: current features use both
localStorage and IndexedDB, and browser internals are not a stable product contract.

## Finish keyboard-shortcut discoverability

The persisted enable/disable setting, guarded shortcut dispatch, and `?` help popup are
already shipped in `js/util/settings.js`, `js/init/kiddopaint.js`, and
`js/util/keyboard-help.js`. The remaining user need is a visible grown-up control for the
setting; today the help popup exposes console commands. Treat comprehensive modifier-key
documentation as a separate fidelity/research task because modifier behavior is independent
of the shortcut setting and is load-bearing for many tools.
